觀察：
- **事實資料的品質不錯**：營業時間衝突有記錄、來源完整、fit15 依規則判斷、缺漏檢查有腳本。

## 2. 規則提案（T7 原本的清單）

### 2.1 推薦指數與分級（`tier`）

**原則：品質分數和「適不適合我們」分開。** 品質是一個分數（地圖上的**大小**），團體、長輩、小孩這些適合程度是篩選條件或**顏色**，不要混成一個數字，否則「好吃但坐不下」和「普通但能包場」會變成同一個分數，反而看不出來。

#### 餐廳品質分數（0～100）
```
Google 修正星數 = (星數 × 評論數 + 4.2 × 50) ÷ (評論數 + 50)      ← 評論少的往 4.2 拉
基礎分 = 食べログ分數在同區的百分位、Google 修正星數在同區的百分位，兩者平均（只有一個就用一個）
推薦加分 = 獨立來源種類（觀光協會精選、觀光三重、日文媒體、中文部落格）每種 +5，最多 +15
分數 = min(100, 基礎分 + 推薦加分)
信心度 = 低：只有一種評分而且評論數 < 20；其他為一般
```
- 4.2 是鳥羽 70 家 Google 星數的中位數，50 是「評論 50 則以上才算可信」的門檻（和納入標準 A 一致）。食べログ分數本身已經對評論數做過修正，不另外打折。
- 用鳥羽試算（腳本暫存，未進 repo）：前段是シーホース、太助、まるみつ寿司、漣、水沼さざえ店；後段是海楽園、王将、長門館。評論只有 12 則、Google 4.8 的もんど岬被拉到中段，符合預期。
- **分級**：S＝分數 85 以上（約前 10%）、A＝60～84、B＝其他。另外「食べログ 3.50 以上而且口コミ 100 則以上」或食べログ百名店，不論分數至少是 A。
- 分數由腳本算（`scripts/score.mjs`，輸出到 `data/derived/`），**不寫回各區的 JSON**；規則改了重跑就好，`tier` 欄位也由腳本產生。

#### 住宿品質分數
- 楽天、じゃらん、Google 各自做同樣的修正（楽天、じゃらん用 4.3／30 則，Google 用 4.2／50 則），取平均。
- 景點和住宿的「推薦程度」也用 0～100，地圖才能用同一套大小。

#### 景點品質分數
- 目前沒有評分，**要補 Google 星數和評論數**（見 §4）。景點的星數大多擠在 4.0～4.5，分不太出來，所以景點改用**人氣**：`log10(Google 評論數)` 在同區的百分位，加上推薦來源數（同餐廳）。
- 景點 S 級另外允許人工指定（例如鳥羽水族館、相差石神さん），寫在 `data/derived/` 的覆寫清單，附理由。

#### 地圖上的表示（給 T11）
| 視覺 | 意義 |
|---|---|
| 大小 | 品質分數（S／A／B 三段，不用連續大小，比較好讀） |
| 顏色 | 依目前模式：全員模式＝`fit15`（yes 綠、split 黃、unknown 灰、no 紅）；分組模式＝類別或情境 |
| 透明度／空心 | 信心度低、或旅程期間有公休日 |
| 角標 | 需要預約、要搭車才到得了、有長階梯 |

### 2.2 搜尋範圍：用「地區」，不用半徑
鳥羽 T4a 按地區搜尋效果很好（缺漏檢查也是照地區做），圓形半徑在海岸、離島地形下沒有意義。
- **建議**：每區先定**子地區**（像鳥羽的「鳥羽站周邊、浦村、相差……」），寫進 `areas.json`（新增 `regions[]`：`id`、`name`、`center`、`contexts`），三種資料點都填正式欄位 `region`（取代 `extra.region` 和景點 `tags` 裡的「鳥羽站周邊」）。
- 步行圈只用在 anchors：車站、景點、住宿步行 **15 分**（套用團體係數後，見 2.4）；不含晚餐的住宿 20 分。

### 2.3 標籤
- **料理種類**（`cuisine` 改成固定清單，可複選）：海鮮丼、壽司、浜焼き・貝、牡蠣、伊勢海老・高級海鮮、定食・食堂、和食・割烹、烏龍麵・蕎麥（伊勢烏龍）、燒肉・肉料理、洋食・義式、咖啡・甜點、居酒屋、其他。原文還是可以寫在 `notes`。
- **價位**（每人，午餐和晚餐分開）：`$` ～1,500 円、`$$` 1,500～3,000、`$$$` 3,000～6,000、`$$$$` 6,000 以上。schema 加數字欄位 `price: { lunch: [min, max], dinner: [min, max] }`，`priceRange` 字串保留給人看。數字欄位之後也拿來估預算。
- **景點、住宿的 `tags`** 也改成固定清單（室內／雨天備案、親子、長輩友善、長階梯、溫泉、包棟……），自由文字不要放 tags。

### 2.4 交通方式與步行
| 項目 | 建議值 |
|---|---|
| 基本步速 | 80 m/分 × OSRM 路線距離（現行） |
| 團體係數 | **全員 1.4**（約 57 m/分）、分組有長輩或小孩 1.2、分組只有大人 1.0 |
| 單段步行上限 | 全員：**套係數後 15 分**；分組：25 分 |
| 一天累計步行（景點內不算） | 全員：約 60 分以內 |
| 超過上限時 | ① 巴士：等車 20 分以內、車程合理，而且路線不是 1 小時以上才一班 → 搭巴士；② 否則計程車：全員 4 台一般計程車，或大型計程車（9 人座）2 台；③ 一整天都在パールロード、相差、國崎、浦村這種巴士稀少的地方 → **建議包車**（大型計程車或小型巴士），費用由 T1b 的 `road-charter.md` 估 |
| 離島 | 以船班為主（T10 補時刻表）；全員上島要確認回程末班船和冬季停航 |

T4c 的 anchors 是用係數 1 算的；改成 1.4 後，原本 15 分的範圍會縮小，**anchors 的分鐘數照原樣存（係數 1 的值），係數在使用時才乘**，這樣改係數不用重算。

### 2.5 每天的行程密度
- 全員日：**主要景點 2 個＋午餐**；09:30 以後出發，**16:30～17:00 回到住宿**（2 月鳥羽日落約 17:20，海邊很冷）。
- 連續兩天內最多一天是「累」的行程（有長階梯、景點內步行 60 分以上、或船程）。
- 到達日（2/2）、最後一天（2/13）不排景點；行程中間至少一個半天自由時間。
- 這些規則給 T14 當警告，不是硬性限制。

### 2.6 團體用餐
- **全員用餐一定要預約**，只能選 `fit15: yes`，或 `split`／`unknown` 但已經打電話確認（新增 `group.confirmed15: { date, note }`）。
- 晚餐預設在住宿吃（一泊二食），餐廳晚餐只排在不含晚餐的住宿那幾天，或刻意安排的一餐。
- 分組（4～6 人）：午餐可以不預約；晚餐、牡蠣小屋這種「完全預約制」的店照店家規定。
- 不接受小孩的店（喜久屋、漁師酒場 鏡）在有小孩的組裡要警告；schema 的 `kids` 改成 `{ allowed: yes|no|age-limit|unknown, minAge, kidsMenu, note }`。

### 2.7 住宿評分門檻
- **排除**：所有評分來源修正後都低於 **3.8**。
- **注意**：3.8～4.0，地圖上顯示，但標示「評價普通」（鳥羽只有彩朝楽 3.85 落在這裡）。
- **沒有評分**的小民宿、包棟（鳥羽有 7 筆）：不排除，標示「無評分」，詳情面板要看得到。

### 2.8 餐廳納入標準（T4a 的 A～F）
保留現行門檻，改四點：
1. **D 的觸發條件加上「旅程中任何一天，這個地區中午 0 家有營業」**（T4c 發現菅島週三、國崎週三週四只剩 0～1 家）。
2. **接受非住客用餐的料理旅館算餐廳**（相差晚上沒有店，伝洋、花椿這類要撈回來）；新增 F③。
3. **離島允許外帶便當當作 D 的保底**（菅島 おかげ屋）。
4. 數量目標：鳥羽 50～70 家剛好。**伊勢（おはらい町）店多很多，目標改成 80～100 家**，數量控制一樣只提高店最多的子地區的 A 門檻。

## 3. 資料夠不夠用（對照之後的使用需求）

| 需求 | 現況 | 缺什麼 | 怎麼補 |
|---|---|---|---|
| **可視化**（地圖） | ✅ 座標、類別、地區都有 | 子地區不是正式欄位；景點沒有評分，畫不出推薦程度；12 個戶外景點沒有「全天開放」的表示法 | §2.2 `region`；§4 補 Google 評分；`hours` 加 `"always": true` |
| **行程規劃 UI** | ⚠️ 營業時間、停留時間、步行時間、時刻表都有 | ① 2 月休業、最後入場都是文字（`febNote`、`hours.note`），程式判斷不了；② 餐廳沒有 `stayMinutes`；③「要搭車」只寫在筆記；④ 住宿 check-in/out 在 `extra`；⑤ 價格是字串，**算不出預算**；⑥ 離島船班沒有時刻表 | ① 新增 `closures: [{ from, to, note }]`、`hours.lastEntry`；② 依料理種類給預設值（食堂 45 分、浜焼き 75 分、套餐 90 分）；③ 餐廳加 `access: walk|car|ferry`；④ 升格 `checkIn`、`checkOut`；⑤ 數字的 `price`、`fares`（大人／小孩整數）；⑥ 併進 T10 |
| **推薦評分** | ⚠️ 餐廳夠；住宿缺 Google；景點完全沒有 | 景點、住宿的 Google 星數與評論數 | §4 用 Places API 補，分數依 §2.1 由腳本算 |
| **摘要**（推薦原因、可能的問題） | ❌ 沒有欄位 | 一段 2～3 句的介紹、優點 2～3 條、注意 2～3 條 | 新增 `summary`（見下），由 Claude 根據已存的事實欄位和來源寫，**不另外大量搜尋** |
| **圖片** | ❌ 0 張 | 每筆 1～3 張 | 見下方「圖片」 |

### 摘要怎麼做
- 格式：`summary: { text, pros: [], cons: [], basedOn: [來源 URL], generated: "2026-xx-xx" }`，繁體中文。
- **「可能的問題」大多可以從結構化欄位直接推出來**：不能訂位、週三公休、2 月休業、長階梯、只有榻榻米、不接受小孩、要搭車、坐不下 15 人。這些用腳本產生，不靠人寫，資料改了會自動更新。
- **「推薦原因」**需要質化資訊：蒐集時已經有讀過的文章（觀光三重、日文媒體、中文部落格），每筆在 `sources[].note` 多記一句「這篇推薦它的原因」（例如「冬季限定的牡蠣吃到飽」），摘要就有根據。這是蒐集流程裡唯一要多做的事，每筆約多 1 分鐘。
- Google 的 AI 摘要（`reviewSummary`、`generativeSummary`）不能存檔（見 §4），而且日本鄉下的覆蓋率不確定，**不拿來當主要來源**。

### 圖片：建議只記 URL，不下載
| 來源 | 適用 | 能不能存 | 備註 |
|---|---|---|---|
| 官網的 `og:image` 或主視覺 | 景點、住宿、部分餐廳 | 只記 URL | 最穩定，代表店家想給人看的樣子 |
| **楽天トラベル API** 的 `hotelImageUrl`、`roomImageUrl` | 住宿 | 照 API 規約顯示（要標示楽天） | 正式 API，順便拿價格和評分（§4） |
| Wikimedia Commons | 景點（神社、燈塔、展望台） | 可以，照授權標示作者 | 授權清楚，可以下載縮圖 |
| Google Places Photos | 全部 | **不能存**，只能即時取用並標示作者 | 只在採用「網站即時呼叫 API」時可用 |
| 食べログ的照片 | — | **不使用** | 照片版權屬投稿者，用程式抓也違反網站限制 |

- schema：`photos: [{ url, page, credit, license, kind: "official"|"wikimedia"|"rakuten"|"google" }]`，`page` 是照片所在的頁面（給人點過去看原圖）。
- **不下載的理由**：版權（大多不是我們能重新散布的）、repo 體積、照片會過時。離線需求（T17）用 PWA 在瀏覽時快取，等同一般瀏覽器快取。
- 例外：Wikimedia 等可以自由使用的照片，可以存縮圖到 `web/public/photos/`。

### 可能遺漏的需求（參考 Wanderlog、Google 地圖清單、TripAdvisor 的做法）
1. **預算估算**：15 人的住宿、餐費、交通、門票總額。需要數字的價格（§2.3、§3）。
2. **預約清單與期限**：哪些要訂、多早要訂、誰訂、訂了沒。`reservation` 加 `leadDays`（幾天前要訂）；T15 已經有規劃清單，但資料要有期限。
3. **旅程期間的特殊日子**：**2/3 節分**（伊勢的神社有活動，也可能人多）、**2/11 建國紀念日**（國定假日）。景點加 `events: [{ date, note }]`。
4. **雨天、強風備案**：`indoor` 已經有；冬季離島船可能停航，行程要有替代方案（T14 標示「有停航風險」的行程段）。
5. **日落時間、氣溫**：2 月日落約 17:20，可以寫死在設定裡，不用蒐集。
6. **15 人共同決定**（投票、留言）：T15 再決定，資料面不用準備。
7. **詳情面板的「附近」**：anchors 已經有；面板只顯示最近 3 個（T4c 建議）。

## 4. 冗餘：哪些用 API 拿更簡單、更準

| 現在的做法 | 替代做法 | 判斷 |
|---|---|---|
| **T4b 在 Chrome 逐家開 Google Maps**，抄星數、評論數、營業時間、座標（從網址解析 `!3d!4d`）、網站欄、臨時休業（71 家 × 約 3～5 次操作） | **Google Places API**：Text Search 找到 `place_id`，Place Details 一次拿 `rating`、`userRatingCount`、`regularOpeningHours`、`location`、`websiteUri`、`businessStatus`、`googleMapsUri` | **建議換**。更準（不用解析網址、不會抄錯）、可以重跑（T18 出發前檢查閉業、營業時間只要跑一次腳本）。費用：這些欄位屬於 Enterprise 等級，每月免費 1,000 次（第三方資料，要再看 Google 價目表），三區約 400～500 個點一次跑完在免費額度內 |
| 景點、住宿**完全沒有 Google 評分**（鳥羽 T3 筆記：「Google 評分全部沒查」） | 同上，用 `place_id` 一次補 | **建議補**，是 §2.1 景點評分的前提 |
| **住宿的價格、評分在楽天頁面上手抄**（`prices` 是「楽天 2027-02-09 的實際報價」） | **楽天トラベル 空室検索 API**（`VacantHotelSearch`）：用座標和 2027-02 的日期查，一次回傳方案名稱、每人或每間價格、`reviewAverage`、`reviewCount`、`hotelImageUrl` | **建議換**。正式 API，免費申請 applicationId，規約要求顯示楽天的標示。價格是真的空房報價，比價目表準。小民宿、包棟沒上楽天的照舊人工查 |
| 餐廳的席數、包廂、包場、小孩、照片（食べログ，Chrome） | **ホットペッパー グルメサーチ API** 有 `capacity`（總席數）、`private_room`、`charter`（包場）、`child`、`open`、`lat/lng`、`photo` | **先測覆蓋率再決定**。CONVENTIONS 說「不使用ホットペッパー，因為難操作」，但那是指網站，API 很好用。問題是鄉下的店很多沒上ホットペッパー，而且沒有「最大予約可能人数」。建議用鳥羽 71 家測一次：超過一半有資料，就當第一輪；食べログ還是分數和團體資訊的主要來源 |
| 座標規定「一律用 Google」 | 景點用 OSM 其實比較好 | **建議放寬**。Google 規約只允許長期存放 `place_id`，座標等其他內容只能短期快取；OSM 的座標可以自由存放（ODbL，標示來源）。規則改成：OSM 有而且位置正確就用 OSM，否則用 Google，並記 `googlePlaceId` |
| OSRM 步行路線 | Google Routes API | **不換**。OSRM 免費、可以快取；Google 的結果不能長期存，還要錢。T4c 的 OSM 路網缺口用「吸附 > 150 m、繞路 > 3 倍」人工檢查就夠 |
| anchors 存在每筆餐廳裡 | 前端用座標即時算 | **維持現狀**。已經是腳本產生的，而且 OSRM 結果有快取；只要記得 anchors 是衍生資料，不要手改 |

**換不掉的（仍然值得花力氣）**：席數、最大予約可能人数、包場條件、階梯和坡道、兒童與長輩票價、2 月休業、團體規定、船班、包車。這些只有食べログ、官網、觀光協會有，也是這個專案資料真正的價值。

### ⚠️ Google 資料能不能存，需要你決定
Google Places 規約：**`place_id` 可以永久存放，其他內容（星數、評論數、營業時間、照片）不能預先抓取、快取或存放**（座標可以短期快取，期限要再看服務條款原文）；顯示時要在 Google 地圖上、或附 Google 標誌，照片和評論要標示作者。
現在 T4b 用 Chrome 手抄 Google 星數存進 JSON，嚴格來說也是存放 Google 內容，**換成 API 並不會讓這件事更合規或更不合規**，只是更省事。可以選：
- **(a) 只存 `place_id`**，網站執行時用 API 即時取星數、照片。最合規，但要有 API key 和代理（T16 本來就要做代理）、每次瀏覽都會用到額度，而且 T5/T11 用的是 MapLibre，不是 Google 地圖。
- **(b) 存 `place_id`，星數等用腳本定期抓到 `data/cache/google/`（不進 git，附抓取日期）**。自用、不公開的折衷做法。
- **(c) 維持現狀**：照舊存在各區 JSON（不論手抄或 API）。
